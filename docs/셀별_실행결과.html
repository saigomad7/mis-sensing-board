칸을 어떻게 읽나

칸무엇범위
rel관련도 — RRF 융합 점수를 1위 대비로 편 것0~1
weight유형 가중 — 사내문서 1.00, 뉴스 0.85, 메일 0.800.80~1.00
recency시의성 — 유형별 반감기로 깎은 값. 사내문서는 안 깎음0~1
adj보정 = 1 − 0.4 × (1 − weight × recency)0.6~1.0
score최종 = rel × adj0~1

★가장 중요한 함정 — 보정을 곱셈으로 걸면 안 된다

RRF 점수는 폭이 매우 좁다(1위 0.0328 ~ 10위 0.0258, 차이 27%). 여기에 시의성(0.5~0.9)을 그대로 곱하면 보정이 관련도를 눌러 버린다.

실측: 벡터 1위·어휘 1위인 표준 문서가 최종 5위로 밀렸다. 4월 문서라 시의성 0.52 로 깎였고 그날치 무관한 뉴스(0.91)가 앞섰다.

→ 시의성은 순위를 뒤집는 힘이 아니라 밀어주는 힘이어야 한다. 보정 힘을 PRIOR=0.4 로 묶어 아무리 낡아도 0.6 아래로 안 내려간다.

표가 임원 화면으로 이어지는 방식

노트북이 만든 조각·벡터를 그대로 써서 화면을 만든다. 로직을 다시 쓰지 않는다 — 서버가 노트북을 불러 그 함수를 쓴다.

축 (임원 관심 테마)
 ├ 그 축의 질문으로 검색 16건
 ├ 점수 하한 — 1위 대비 55% 미만은 요약에서 뺀다
 ├ 카테고리로 나눔 — 시장 · 전망 · 기준 · 사내 · 논의
 ├ 카테고리마다 조각을 묶어서 모델에 한 번에
 └ 카테고리별 한 줄 + 축 판단 + 지난번 대비 변화

축 하나당 모델을 한 번만 부른다

카테고리마다 따로 부르면 축 5개 × 카테고리 5개 = 25번이 된다. 묶어 물으면 5번으로 끝난다. 지난 기록 대조도 같은 호출에 얹는다.

축 요약은 카테고리 요약을 다시 요약한 것이 아니다. 같은 호출에서 원문 청크를 보고 만든다 — 두 번 압축하면 사내↔외부 충돌을 못 잡는다.

★공백을 감추지 않는 것이 핵심이다

전에는 하한에 걸린 카테고리가 조용히 사라졌다. "이 축에 사내 문서가 없다" 는 그 자체로 임원이 봐야 할 정보인데 가려졌다.

실측 — 사내 문서가 없는 축이 3개다. 장비·설비투자 / 공정·표준 / 일반 DRAM·수급. 표준이 바뀌었는데 우리 대응 문서가 없다는 뜻이다.

왜 하한이 몫보다 나은가 — 브리핑에서만

억지로 남긴 근거는 요약에 들어가고, 요약은 임원이 그대로 읽는다.

HBM 축에 "장비 출하 통계"(0.47)를 기준 줄로 넣으면
  기준: 국내 장비 출하가 18% 늘었다
  → 임원은 HBM 표준 이야기로 읽는다. 아무 관계가 없는데도.

같은 사내문서 하나가 세 축의 '사내' 줄을 다 채우기도 한다
  DRAM 수급 0.37 · 공정 표준 0.41 · 장비투자 0.42
  → 남기면 세 축에 똑같은 문장이 반복된다.

모델이 없을 때

축 요약 자리에 요약 아님 배지가 붙고 첫 조각을 잘라 쓴다. 구조는 전부 확인되지만 문장은 요약이 아니다. .env 에 LLM_BASE_URL·LLM_MODEL 을 채우면 사라진다.

⑧ run_once

운영 — 새 문서가 들어오면 이 셀 하나

첫 실행
run_once : {"new_raw": 10, "new_docs": 10, "new_chunks": 36,
            "new_vectors": 36, "failed": 0, "seconds": 0.3}

두 번째 — 새 문서가 없으면
run_once : {"new_raw": 0, "new_docs": 0, "new_chunks": 0,
            "new_vectors": 0, "failed": 0, "seconds": 0.0}

매일 돌려도 안전하다. 새 문서·고쳐진 문서만 처리된다. failed 가 0이 아니면 그 건만 실패한 것이고 나머지는 정상 처리됐다.

규칙을 고쳤을 때

reset() 후 run_once(). 정규화·조각 규칙을 바꾸면 이미 만든 것은 자동으로 다시 안 만들어진다 — 지우고 다시 돌려야 한다.

사내 반입

실제 문서로 바꿨을 때 볼 순서

  1. found_tbl 의 access — 권한이 제대로 붙었나. 전부 '전사' 면 여기서 멈춘다
  2. shrink_tbl 의 kept_pct — mail 이 90% 이상이면 사내 서식이 안 지워진 것
  3. ③-b 셀 — 무엇이 남았는지 원문과 나란히 확인
  4. loss_tbl 의 kept_pct — 90% 아래면 내용이 사라진 것. n_chunks 가 1이면 절이 안 잡힌 것
  5. vec_tbl 의 model — fake 면 순위를 믿지 않는다
  6. ⑥-c 비교 실험 — 어휘 갈래가 실제로 도움이 되는지
  7. check_tbl — 위반이 있으면 지시문·근거 개수를 조정
  8. 화면 — python web/server.py. 사내 문서가 없는 축이 몇 개인지 상단 KPI 에서 본다. 많으면 축 정의가 사내 자료와 안 맞는 것이다

모델 없이 4번까지 확인된다

①~④ 는 코드만 돈다. 사내 모델을 붙이기 전에 파싱·조각이 제대로 되는지 먼저 확인하는 것이 순서상 맞다. 거기서 DRM·발행일·절 표기 문제가 다 드러난다.
