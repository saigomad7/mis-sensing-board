# 마켓 센싱 보드

임원이 30초 안에 훑고 궁금한 축만 펼쳐 보는 화면과,
그 화면을 만드는 적재·검색 파이프라인.

```
① collect → ② raw → ③ normalize → ④ chunk → ⑤ embed → ⑥ search → ⑦ answer
                                                            │
                                                         ⑧ 화면
```

## 파일 셋

| 파일 | 무엇 | 언제 여나 |
|---|---|---|
| **`sensing_pipeline.py`** | 한 셀씩 실행하며 흐름을 보는 노트북. **사내 문서에 맞춰 손볼 로직**이 여기 있다 | Spyder 로 연다 |
| `sensing_tools.py` | 배관 — `.env` · 모델호출 · DB · Milvus · 표보기 | 안 연다 |
| `web/server.py` · `web/index.html` | 화면 — **로직은 없다.** 노트북 함수를 불러 실어 나른다 | 거의 안 연다 |

> **축·하한·지시문은 전부 노트북 ⑨ 절에 있다.**
> `AXES` · `CAT_FLOOR` · `SUMMARY_SYSTEM` · `build_axis` · `build_brief`.
> 노트북에서 셀을 돌려 확인한 것이 곧 화면에 나오는 것이다.

> 이전 폴더(`MIS_학습노트_260908`)와 **파일 이름이 겹치지 않게** 바꿨다.
> 로직은 같고, 화면 개선이 더 들어가 있다.

## 시작

```bash
cp .env.example .env          # 값을 채운다 (아래)
python sensing_pipeline.py    # 적재 — 또는 Spyder 로 한 셀씩
python web/server.py          # 화면 → http://127.0.0.1:8700
```

`pip install` 이 필요 없다. **표준 라이브러리만** 쓴다(폐쇄망 대비).
`.env` 를 안 채워도 돈다 — 가짜 벡터로 흐름은 전부 확인된다.

## 사내에서 갈아끼울 곳 — `.env` 값 셋

```
① 임베딩 모델   EMBED_BASE_URL · EMBED_MODEL      ⑤ 벡터 · ⑥ 검색
② 생성 모델     LLM_BASE_URL · LLM_MODEL          ⑦ 답변 · 축 요약
③ 벡터 저장소   VECTOR_KIND=milvus · MILVUS_URI   ⑤ 저장 · ⑥ 검색
```

**코드는 손대지 않는다.**

## 노트북 셀 구성

```
준비 · 0 표만들기
① collect  ② save_raw  ③ normalize  ③-b 전후비교
④ chunk    ④-b 저장본vs임베딩본       ⑤ embed   ⑤-b Milvus
⑥-a bm25   ⑥-b search  ⑥-c 비교실험  ⑦ answer
⑨-a 주제축  ⑨-b 축 하나  ⑨-c 지난 기록 대조  ⑨-d 화면으로 보기
⑧ run_once · reset
```

**⑨ 절이 화면을 만드는 곳**이다. 셀에서 돌려 확인한 결과가 그대로 화면에 나온다.

## 화면이 만들어지는 순서

```
축 (임원 관심 테마)
 ├ 그 축의 질문으로 검색 16건
 ├ 점수 하한(1위 대비 55%)을 넘긴 것만 카테고리로 나눔
 ├ 카테고리마다 조각을 묶어 모델에 **한 번에** 넘김
 └ 카테고리별 한 줄 + 축 판단 한 줄 + 지난번 대비 변화
```

**축 하나당 모델을 한 번만 부른다.** 카테고리마다 따로 부르면 25번이 된다.
**축 요약은 카테고리 요약을 다시 요약한 것이 아니다** — 같은 호출에서
원문 청크를 보고 만든다. 두 번 압축하면 사내↔외부 충돌을 못 잡는다.

## 마켓 센싱으로 쓰려고 넣은 것

| 무엇 | 왜 |
|---|---|
| **점수 하한** | 빈칸을 억지로 채우면 없는 이야기를 지어낸다 |
| **빈 카테고리를 명시** | "이 축에 사내 문서가 없다" 는 그 자체로 정보다 |
| **관련 낮음은 접어서 보관** | 날아가지도 않고 거짓말도 안 한다 |
| **지난 기록과 대조** | 센싱의 핵심은 "지금 무엇" 이 아니라 **"무엇이 달라졌나"** |
| **축은 요약이 아니라 판단** | 사내↔외부가 어긋나는 곳을 먼저 짚는다 |
| **변화 큰 축이 위로** | 임원이 스크롤하지 않게 |
| **해석은 한 축만, 사실은 여러 축** | 같은 뉴스가 다섯 축에 반복되면 신뢰를 잃는다 |

### 왜 하한이 몫보다 나은가 (브리핑에서만)

**억지로 남긴 근거는 요약에 들어가고, 요약은 임원이 그대로 읽는다.**
HBM 축에 "장비 출하 통계"(0.47)를 `기준` 줄로 넣으면
*"기준: 국내 장비 출하가 18% 늘었다"* 가 되어 **HBM 표준 이야기로 읽힌다.**

같은 사내문서 하나가 세 축의 `사내` 줄을 다 채우기도 한다(0.42·0.41·0.37).

**질의응답은 반대다** — 사용자가 직접 읽고 판단하므로 유형별 몫이 낫다.
`sensing_pipeline.py` 의 `search()` 는 그대로 두었다.

## 보안

- 키·주소를 코드에 넣지 않는다. 전부 `.env` 경유.
- `.env` · `sensing.db` 는 커밋되지 않는다.
- 검색은 **권한을 가장 먼저** 거른다. 상단에서 바꾸면 화면의 행이 실제로 달라진다.
- `문서/` 에 **사내 실제 문서를 넣지 않는다.** `DOC_DIR` 로 사내 폴더를 가리킨다.
